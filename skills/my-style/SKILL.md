# Мой стиль кода

С этого момента пиши и правь код только так. Если правишь чужой код, в этом стиле переписывай только то, что трогаешь.

## Главное правило

Делай только то, что нужно для цели. Прежде чем что-то добавить, спроси себя: сломается ли задача без этого? Если нет, не добавляй.

Не нужно:
- поддерживать старые форматы, отладочные режимы, лишние флаги и переменные окружения, «на всякий случай»;
- запасные значения для полей, которые всегда есть: пиши `doc["field"]`, а не `doc.get("field") or "unknown"`;
- try/except вокруг всего подряд. Ошибка должна падать. Ловить её стоит, только если без этого задача не выполнится, например отчёт должен уйти, даже если упал необязательный шаг;
- свои классы исключений и обёртки, которые переупаковывают сообщения;
- эвристики, которые чинят ответ другой системы. Правильнее починить источник;
- проверки того, что уже гарантирует другая часть системы.

## Как писать

- Простые функции на уровне модуля. Классы только там, где без них никак.
- Настройки — константы `UPPER_CASE` в начале файла или в одном `config.py`. Окружение читай через `os.getenv("X") or "default"`.
- Явный `if / elif / else` вместо тернарников внутри выражений.
- Обычный `for` с накоплением в список вместо вложенных comprehension, `**({...} if ... else {})` и `lambda` в данных.
- Промежуточные переменные с понятными именами вместо выражения в одну строку.
- Имена функций — глагол и объект: `get_hosts`, `build_incidents`, `extract_changes`.
- Одно назначение — одна функция. Дублирующиеся хелперы держи в одном месте.
- Не заводи функцию-однострочник ради одного вызова и обёртки, которые просто зовут другую функцию: пиши выражение на месте.
- Структура плоская: без пустых `__init__.py`, без папок ради одного файла.
- CLI — `argparse` с короткими `help` по-русски.
- Сообщения пользователю и в stderr — по-русски, коротко: `[error] ...`, `[warn] ...`.

## Комментарии

- Без docstring-ов, которые пересказывают имя функции.
- Без комментариев «что делает строка» и без истории изменений («добавлено для…», «раньше было…»).
- Допустимы короткие маркеры секций (`# failed`, `# changed`) и одна строка там, где без неё неочевидно *почему*.

## README

Коротко и по-человечески, по-русски. Нужные разделы:
1. Что это и зачем — пара предложений.
2. Как запустить — команды и переменные окружения.
3. Что получится на выходе.
4. Если что-то не так — таблица «симптом → причина».

Без описания внутренностей, которое видно из кода.

## Когда тебя поправили

Если пользователь поправил код или сказал, что ему что-то не нравится в том, как написано, а правка касается стиля, а не конкретной задачи, сразу допиши правило в этот файл:

- Править нужно исходник `/etc/nixos/skills/my-style/SKILL.md`. Файл `~/.claude/skills/my-style/SKILL.md` — это ссылка в nix store, и она только для чтения.
- Одно правило — одна короткая строка в подходящем разделе. Если правило противоречит уже записанному, замени старое, а не добавляй рядом.
- Не записывай то, что относится только к текущему проекту или задаче.
- После правки скажи одной строкой, что добавил. Напомни, что правило заработает в новых сессиях после `sudo nixos-rebuild switch --flake /etc/nixos`, а в текущей сессии просто следуй ему.

## Пример

Не так:

```python
def host_facts(h):
    """Что известно о хосте: os/arch из фактов ARA, остальное из групп inventory."""
    g = h.get("groups", [])
    pick = lambda p: next((x.removeprefix(p) for x in g if x.startswith(p)), None)
    return {"os": h.get("os") or ("Proxmox VE" if "proxmox" in g else "unknown"), **({"arch": pick("arch_")} if g else {})}
```

А так:

```python
def host_facts(h):
    groups = h["groups"]

    def pick(prefix):
        for g in groups:
            if g.startswith(prefix):
                return g.removeprefix(prefix)
        return "?"

    return {
        "device_role": pick("device_roles_"),
        "os": h["os"] or "unknown",
        "arch": h["arch"] or "unknown",
    }
```
